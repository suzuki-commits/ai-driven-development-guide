何を読ませるか。何を許すか。何をもって完成とするか。どこで止めるか。Claude Code を使った開発の成果は、モデルの外側にあるこの4つの設計で大きく変わります。要諦・設定方法・注意点・当社で実際に起きた事例の順にまとめました。

要諦 設定方法 注意点 実施事例

何を大事にするか

要諦

7つの原則です。それぞれに、4つの層のどこを設計する話なのかを付けています。

確かめる

仕様が先、実装は後

Plan モードで調べてから SPEC を書きます。成功基準は「npm test が通る」のように、確かめられる形で書きます。そのあと /clear してから実装に入ります。複数ファイルにまたがる変更は、必ずこの2段階に分けます。

読ませる

コンテキストは足すより絞る

毎回読ませる指示は最小限にし、詳しいルールは関係する作業のときだけ読ませます。読ませすぎると、判断の基準がぼやけます。

確かめる

検証できて初めて完成

書き上がっただけでは未完成です。実行したうえで、ツールの「成功」表示ではなく、実ファイル・受信側・画面などの別の経路で確かめて、初めて完成とします。

許す

守りは何重にも。文章のルールは破られる前提

権限設定（禁止）、フック（機械チェック）、人間の承認の3段で守ります。同じ違反が再発したら、文章のルールをフックに置き換えます。

許す

役割を分ける

設計・判断する役、実装する役、軽作業の役に分け、役割ごとに使える道具とモデルを決めます。書いた本人にレビューさせません。

止める

失敗したら上塗りせず巻き戻す

失敗の記録が残ったまま続けると、精度が落ちます。巻き戻すか、同じ失敗が2回続いたら /clear して、学んだことだけを持ち込んでやり直します。

読ませる 止める

繰り返す作業は型にする

同じ作業を3回したら、スキルにします。作るときに「何をもって役立ったとするか」と「いつ捨てるか」も書いておきます。

どう設定するか

設定方法（最小構成）

上から順に整えていけば、最小限の守りと型がそろいます。

  1. Step0

    起動するフォルダで作業範囲を区切る

    Claude Code が読み書きできる範囲は、起動したフォルダが基準になります。Windows ネイティブ環境ではサンドボックス機能が使えなかったため（当社確認時点）、案件ごとにそのフォルダへ移動してから起動することが、事実上の隔離になります。

  2. Step1

    CLAUDE.md にプロジェクトの基本ルールを書く

    書くのは「コードを読んでも分からないこと」だけです。長くなったら .claude/rules/ に分け、paths: を指定して、関係するファイルを編集するときだけ読み込ませます（事例6）。

  3. Step2

    権限を「禁止・確認・許可」に分ける

    書き込み禁止は Edit(パス) の形で書きます。これで Write や NotebookEdit も一緒に止まります。Write(パス) の形は効かないので注意してください（事例2）。

  4. Step3

    フックで機械的にチェックする

    • フックへの入力は、標準入力の JSON で届きます。
    • exit 2 で止めると、エラー出力の内容が Claude に返ります。
    • Stop フックは stop_hook_active を見て、無限ループを防ぎます。
    • 想定外のエラーでは exit 0 にして、作業そのものは止めません。
    • 作ったら、わざと引っかかるコマンドで本当に作動するかを試します（事例3）。
  5. Step4

    サブエージェントで役割を分ける

    model は必ず書きます。書かないと、メインの高いモデルで動きます。tools を読み取り系に絞れば、レビュー役が勝手にコードを直すことはありません。

  6. Step5

    繰り返す作業をスキルにする

    「やること」「やらないこと」「出力の形」の3つに分けて書くと、毎回同じ品質で返ってきます。

  7. Step6

    日々の操作を覚える

    計画から始める
    Shift+Tab で Plan モードに切り替える
    別のタスクに移る
    /clear
    会話が長くなってきた
    /compact 次にやること（早めに、次の作業を添えて）
    やり方が失敗した
    Esc を2回押して巻き戻す
    本筋と関係ない質問
    /btw 質問（会話の記録に残らない）
    最後まで走らせたい
    /goal 検証条件（条件を満たすまで作業を続ける）
    複数の機能を並行で開発
    claude -w 名前（git worktree で作業場所を分ける）
    コストを確かめる
    /usage

どこでつまずくか

注意点

  • 設定は「書いた」ではなく「効いている」かを確かめる

    設定の優先順位の仕組みやバージョン変更で、意図と逆に効くことがあります（事例1〜3）。

  • 権限ルールは、省略された項目には効かない

    たとえば Agent(model:*) と書いても、model を指定しない委譲は止められません。ルールで止められないものは、運用ルールと定期チェックで補います。

  • 自動承認モードは、速さと安全の引き換え

    使うなら、取り返しのつかない操作を deny と ask で先に固めておきます。末尾の一部だけで判定するような広すぎる許可ルールは作りません。

  • 公開・送信・削除・上書きは、最初から全自動にしない

    この4つだけは、人間の承認を残します。

  • サブエージェントの結果は自動で反映しない

    レビューの指摘も、人が一度見て採否を決めます。

  • 会話が長いほど精度が落ちる

    劣化が始まる量はタスクによって違います。余裕のあるうちに /compact します。

  • model を指定しない委譲はコストが高くなる

    指定がないとメインモデルの単価で動きます。内訳は /usage で確認できます。

実際に何が起きたか

実施事例

コミクス社内の Claude Code 運用で、実際に起きたことです。いずれも現在は修正・運用済みです。

確かめる

設定がモデル指定を丸ごと上書きしていた

何があったか
サブエージェントのモデルを環境変数 CLAUDE_CODE_SUBAGENT_MODEL で指定したところ、各エージェント定義に書いた model 指定がすべて上書きされていました。撤去するまで、上位の役割も軽作業の役割も同じモデルで動いていました（その後のバージョンで、未指定時の既定値として働く仕様に変わりました）。
学び
設定は意図と逆に効くことがある。実際に動いたモデルをログに残し、定期的に集計して確かめる。
許す

書き込み禁止のつもりが効いていなかった

何があったか
.env の書き込み禁止を Write(パス) の形で書いていたため、ルールが無効でした。遮断したつもりで、Write ツール経由の上書きは通る状態でした。
学び
起動時の警告を読む。書き込み禁止は Edit(パス) の形で書く。
許す

守りのフックが一度も作動していなかった

何があったか
危険コマンドを止めるフックが、入力の受け取り方が環境変数から標準入力の JSON に変わったことで、実際には作動していませんでした。権限設定の deny が別の段で止めていたため、被害はありませんでした。
学び
守りの仕組みは、本当に作動するかテストする。一段だけに頼らない。
止める

ルールで禁止しても3回再発した

何があったか
python -c "…" の中にバッククォートが混ざると、コマンドが途中で分断され、名前の壊れたファイルができます。ルール文書で禁止した後も、3回起きました。
学び
文章のルールは守られない前提で考える。再発したら、フックで機械的に止める。
確かめる

「完成しました」を機械でチェックする

何があったか
ツールの成功表示を信じて「完成」と報告したのに、成果物ができていない。そんな偽の成功報告が起きていました。そこで、完了報告に書いた成果物のパスが実在しなければ作業の終了をブロックする仕組みを入れました。誤作動を避けるため対象は成果物の保存フォルダだけに絞り、想定外のエラーでは止めず、強制は1回だけにしています。
学び
完成の判定を人の目だけに頼らない。対象を狭くして、誤検知を減らす。
読ませる

毎回読ませるルールを約37%減らした

何があったか
毎回読み込んでいたルールを、関係するファイルを編集するときだけ読み込む形（paths: 指定）に切り替え、毎回の読み込み量を約37%減らしました。
学び
毎回読ませる量は、思ったより絞れる。絞ったぶんコストが下がり、必要なルールが埋もれにくくなる。
許す

モデルを3層に分けた

何があったか
設計・判断の司令塔、実作業、軽作業の3層にモデルを分け、最上位のモデルは条件を満たしたときだけ呼ぶ「切り札」にしました。委譲するときは model の明記を必須にしています。
学び
役割分担はコストにも品質にも効く。ただし、運用ルールと定期監査をセットで回す。
止める

承認の依頼を3つに仕分けた

何があったか
AIからの確認依頼が多すぎて、代表の判断が詰まりました。そこで「すぐ確認（取り返しがつかない・社外・お金）」「週1回まとめて裁定」「既定値で処理」の3つに分けました。
学び
AI駆動開発のボトルネックは、人間の承認の手間。承認の仕組みも、開発の一部として設計する。
